论文阅读：UI-TARS - Pioneering Automated GUI Interaction with Native Agents

发表于2026-11-05|更新于2026-11-05
|总字数:4.8k|阅读时长:15分钟|浏览量:—

引：UI-TARS 将 GUI agent 中的感知、动作选择和部分工作流程，放进一个接收截图、生成操作的 VLM。本文最值得关注的是它怎样构造训练数据：从界面元素理解到多步轨迹，再到模型亲自执行后产生的错误与纠正。尤其是 在失败之后的状态上训练恢复动作，直接关系到为什么离线 SFT 表现良好，仍可能无法完成真实交互任务。

背景

让模型操作电脑，至少要把三个问题接起来：看懂当前页面，确定下一步做什么，再把这个意图落到具体控件的坐标和动作上。例如“将文件另存为 PDF”，既涉及菜单与对话框的操作顺序，也涉及找到“文件”“导出”等按钮。

早期系统可以用规则描述每一步；后来常见的 agent framework 则用通用大模型，加上提示词、解析器、记忆和规划等模块来组织过程。UI-TARS 希望把更多任务经验通过训练写入模型参数，使同一个模型直接根据截图和历史产生动作。

这里的 native agent model 是作者对模型化 agent 的定位。它仍然需要动作执行器、运行环境和训练数据管线，并不意味着模型权重可以独自完成全部系统工作。论文关于主动终身学习的讨论也是后续方向；本文实际采用的在线数据迭代，仍包含规则、其他模型和人工审核。

核心能力

作者先将 GUI agent 的能力分为感知、动作、推理和记忆。它们对应不同层面的训练与评估：

能力 具体对象 典型检查方式
感知 文字、图标、布局和状态变化 截图问答、界面描述
Grounding 指令所指元素在屏幕中的位置 预测点是否落在目标框内
动作与推理 根据任务和历史选择下一步操作 静态轨迹的单步动作匹配、实际任务执行
记忆 当前任务历史与此前学到的操作经验 长任务中能否利用已有信息、避免重复错误

尤其需要区分 离线动作评估 和 在线任务评估。前者把固定截图与历史给模型，检查下一步输出；后者真的执行动作，让模型面对由自己此前操作产生的新页面。离线评估没有完整检验一次误点后接下来会发生什么。

UI-TARS

整体结构

原论文 Fig. 4。上部是截图、思考和操作构成的交互过程，下部是各项能力对应的训练数据。

UI-TARS 基于 Qwen2-VL。给定任务指令，第 iii 步读取截图 oio_ioi​，先产生文本形式的 thought tit_iti​，再生成动作 aia_iai​。一次完整交互可以写成：

(instruction,(o1,t1,a1),(o2,t2,a2),…,(on,tn,an)).(\text{instruction},(o_1,t_1,a_1),(o_2,t_2,a_2),\ldots,(o_n,t_n,a_n)). (instruction,(o1​,t1​,a1​),(o2​,t2​,a2​),…,(on​,tn​,an​)).

例如，模型看到导出对话框，可以先记录“保存类型还不是 PDF，需要展开类型菜单”，再输出点击位置。执行器把动作送入系统，取得下一张真实截图，模型再决定后续步骤。截图来自环境，不是模型自己预测出的下一帧。

作者保留历史动作和 thoughts 作为任务上下文，而高开销的截图只保留最近若干张，以适应约 32k 的上下文预算。这里的短期记忆是输入中的交互记录；长期经验则主要通过后续训练进入参数，不是另加一个检索数据库。

界面感知

GUI 截图有一个特点：信息密度很高，关键目标可能只是高分辨率屏幕上的一个小图标。只训练“这是一张网页”的粗粒度描述，无法提供足够的定位和操作信息。

作者在收集截图时，同步利用解析工具取得元素类型、边界框、文字、层次等 metadata，再将它们转换为训练任务：

  • 元素描述：描述按钮、文本框等元素的外观、位置和功能；
  • 密集描述：把单个元素整合成保留界面布局的整体说明；
  • 状态变化描述：比较前后截图，识别点击、输入或非交互变化造成的差异；
  • 界面问答：根据截图回答内容与操作相关的问题；
  • Set-of-Mark：结合带标记的元素学习识别与定位。

这里要区分数据构造与模型使用： 训练数据可以借助结构化 metadata 生成监督，部署时模型仍以截图作为视觉观察。如果看到数据管线用了边界框或解析器，不能据此判断策略推理时也必须取得 DOM 或可访问性树。

状态变化描述尤其贴近交互。按钮被点击后，页面可能只出现一个小勾选标记；也可能因动画发生变化，却没有完成目标。通过前后截图监督，模型学习关注的是“动作之后发生了什么”，而不只是当前画面上有哪些控件。

动作与 grounding

作者将不同平台语义接近的动作统一表示，并保留平台专用操作。共用动作包括点击、拖动、滚动、输入、等待、结束与请求用户介入；桌面额外包含快捷键、双击、右键，移动端额外包含长按、返回和主页等。

例如，论文中的动作接口包含 Click(x, y)、Type(content)、Finished() 和 CallUser()。同一种“选中目标”意图在电脑和手机上可以共享部分监督，但不能把所有平台差异都压成同一种操作。

对于需要坐标的动作，作者用元素描述与截图组成输入，以边界框中心作为点标签，并将坐标按屏幕尺寸归一化。模型要学会把“右上角写着 Submit 的红色按钮”对应到屏幕位置。输出归一化坐标后，执行侧再结合当前尺寸转换为实际位置。

多步行为则来自人工录制轨迹与已有 GUI 数据集。作者把不同数据集中的动作格式统一，再训练模型根据任务、历史和当前截图选择动作。Grounding 提供“在哪里”的监督，多步轨迹提供“现在应该操作什么”的监督；只提高前者，不足以解决顺序规划错误。

推理数据

作者用两类来源补充推理能力。

第一类是图文交错的软件教程。从 MINT 与 OmniCorpus 中先用 fastText 粗筛，再用 LLM 细筛、去重和清理，整理出约 600 万篇 GUI 教程，平均约 510 个文本 token、3.3 张图片。它们提供了操作知识与步骤组织，但与真实设备上的逐步动作轨迹仍是不同数据。

第二类是给已有动作轨迹补充 thought。作者希望这些文本包含任务分解、目标保持、里程碑识别、尝试和反思等模式，让“为什么此时执行这个动作”也成为模型可学习的序列。

ActRe 在标注第 nnn 步 thought 时，会把目标动作 ana_nan​ 也提供给标注 VLM。可以把它理解为：动作标签已经知道，让模型结合前文为这一步补充说明。这个动作是数据构造时的额外信息，真实推理时不能提前取得。

这也会产生一个问题：解释可能只是对已知动作的事后合理化。于是作者进一步做 thought bootstrapping：让早期 UI-TARS 在不知道目标动作的情况下采样多组 thought-action，再保留预测动作与标签一致的候选。这样减少了提前泄露动作对标注过程的影响，但“动作匹配正确”本身仍不能证明每一句 thought 都是正确的因果解释。

训练数据既包含带 thought 的轨迹，也包含直接输出动作的轨迹。因此，模型并不是只能用一种固定长度的推理格式行动。

在线轨迹

只有离线专家轨迹，还没有覆盖模型自己误操作后的页面。作者因此让当前模型在数百个虚拟 PC 上实际执行任务，再筛选产生的新轨迹。

原论文 Fig. 7。模型执行任务后，轨迹经过规则、人工与 VLM 过滤，再用于更新模型与任务集合。

设第 nnn 轮模型是 MnM_nMn​，任务集合是 In\mathcal{I}_nIn​。执行后得到原始轨迹 Traw,n\mathcal{T}_{\mathrm{raw},n}Traw,n​，筛选为：

Mn+1=FineTune(Mn,Tfiltered,n).M_{n+1}=\mathrm{FineTune}(M_n,\mathcal{T}_{\mathrm{filtered},n}). Mn+1​=FineTune(Mn​,Tfiltered,n​).

筛选包括规则剔除明显异常，例如反复无效操作；VLM 对轨迹评分；以及人工检查部分轨迹，找到错误位置、保留有效前缀。每轮还会由人工完善与扩充任务集合，再开始下一轮采集。

这个过程的关键是新数据来自 当前模型与真实交互环境共同产生的状态，并经过质量判断后才进入训练。这里的 online 描述数据采集来自交互，并不表示产品运行时每做一步就立即更新参数，也不表示所有模型输出都能直接作为正确标签。

反思训练

单纯保留成功轨迹和有效前缀，可以学习正确操作，却可能继续缺少恢复样本。UI-TARS 因此在错误位置构造两类配对数据。

第一类是 错误纠正。假设第 τ\tauτ 步的 thought-action 为 (tτ,aτ)(t_\tau,a_\tau)(tτ​,aτ​)，人工标出更合适的 (tτ∗,aτ∗)(t^*_\tau,a^*_\tau)(tτ∗​,aτ∗​)。正负样本拥有相同的前缀与当前观察，只在这一步的输出不同。它教模型在错误发生之前选对。

第二类是 错误发生后的恢复。保留第 τ\tauτ 步已经执行的错误，以及它产生的新截图 oτ+1o_{\tau+1}oτ+1​，再标出下一步正确的 (tτ+1∗,aτ+1∗)(t^*_{\tau+1},a^*_{\tau+1})(tτ+1∗​,aτ+1∗​)。它教模型在已经偏离原计划时继续行动。

举个例子，本来要收藏网页，却误点关闭标签页。第一类样本教模型在原页面正确点击收藏；第二类样本的输入已经是标签页关闭后的页面，标签应该是恢复刚关闭的标签页，再继续任务。两者不能互相替代，因为面对的环境状态不同。

在 SFT 中，作者使用正样本， 只对人工纠正的步骤计算损失。历史里的错误动作可以作为理解当前状态的上下文，但不作为需要模仿的目标。否则同一条样本一边解释“这是错误”，一边又用交叉熵奖励模型复现它，监督就发生了冲突。

Agent DPO

纠正训练只使用正输出，而在线采集还留下了对应的负输出。作者进一步用 DPO，让模型在相同状态上下文下偏好纠正动作。

用 sτs_\tausτ​ 概括当时的任务与交互上下文，aτa_\tauaτ​ 为原错误动作，aτ′a'_\tauaτ′​ 为偏好的纠正动作。论文使用的目标为：

LDPO(θ)=−Eτ[log⁡σ(βlog⁡πθ(aτ′∣sτ)πSFT(aτ′∣sτ)−βlog⁡πθ(aτ∣sτ)πSFT(aτ∣sτ))].\begin{aligned} \mathcal{L}_{\mathrm{DPO}}(\theta) =-\mathbb{E}_{\tau}\Bigg[\log\sigma\Bigg( &\beta\log\frac{\pi_\theta(a'_\tau\mid s_\tau)} {\pi_{\mathrm{SFT}}(a'_\tau\mid s_\tau)}\\ -&\beta\log\frac{\pi_\theta(a_\tau\mid s_\tau)} {\pi_{\mathrm{SFT}}(a_\tau\mid s_\tau)} \Bigg)\Bigg]. \end{aligned} LDPO​(θ)=−Eτ​[logσ(−​βlogπSFT​(aτ′​∣sτ​)πθ​(aτ′​∣sτ​)​βlogπSFT​(aτ​∣sτ​)πθ​(aτ​∣sτ​)​)].​

其中 πSFT\pi_{\mathrm{SFT}}πSFT​ 是固定的 SFT 参考模型，πθ\pi_\thetaπθ​ 是正在优化的模型，σ\sigmaσ 是 sigmoid，β\betaβ 控制相对参考策略的约束强度。比较的是两个输出相对参考模型的概率比，希望纠正动作获得更大的相对优势。

这与“再多做一次正样本 SFT”有区别：目标里显式出现同一上下文中的负动作。DPO 直接优化偏好对，不需要在这一步额外训练一个独立奖励网络，也不等同于运行 PPO 之类的在线策略梯度算法。收益仍然依赖正负样本确实对应可比较的状态，以及纠正标签是否可靠。

训练阶段

整体训练使用约 50B token，分为三个阶段：

  1. Continual pre-training：使用感知、grounding、教程和动作轨迹等数据，先学习广泛的 GUI 知识；这一阶段不加入 reflection tuning 数据。
  2. Annealing：选择更高质量的数据子集，并加入反思纠正样本，得到 UI-TARS-SFT。
  3. DPO：使用在线反思过程得到的偏好对，得到 UI-TARS-DPO。

因此，论文中的 SFT 和 DPO 结果需要分别标注。不能把不同阶段、不同规模、不同平台上的最好数值拼成一个模型的统一成绩。

实验

感知与定位

感知评估包括 VisualWebBench、WebSRC 与 ScreenQA-short，分别覆盖网页理解、结构语义和手机截图问答。Table 3 中，UI-TARS-72B 的 VisualWebBench 为 82.8，7B 的 WebSRC 为 93.6；不同任务上并非都是参数最多的版本最好。

Grounding 的指标主要是预测位置是否落在目标元素框内，越高越好。下面摘出 Table 4–6 的平均成绩：

模型 ScreenSpot ↑ ScreenSpot v2 ↑ ScreenSpot Pro ↑
UI-TARS-2B 82.3 84.7 27.7
UI-TARS-7B 89.5 91.6 35.7
UI-TARS-72B 88.4 90.3 38.1

普通 ScreenSpot 上，72B 没有超过 7B；更复杂、分辨率更高的专业软件场景中，72B 的 Pro 成绩更高。但 Pro 仍明显低于普通任务，说明小目标和专业界面定位并未解决。定位准确率也不能直接当成完整任务成功率。

离线 agent

Multimodal Mind2Web 给出固定历史，检查模型的下一步元素、操作与参数；UI-TARS-72B 在跨任务、跨网站、跨领域划分上的 Step SR 分别为 68.6、63.5、62.1，见 Table 7。AndroidControl 与 GUI Odyssey 则覆盖手机任务和跨应用操作。

这些结果说明模型能够在已给定的状态上较好地选择下一步。实际执行时，前面的错误会改变此后的输入，因此不能把这些单步比例直接外推成完成十几步任务的成功率，也不能假定每步错误相互独立后简单相乘。

显式推理

作者还让同一个 7B 模型在推理时选择带 thought 或直接输出动作。在域内离线任务上，只采样一次时，带 thought 的结果反而略差；作者观察到额外推理可能引入错误信息或不合适的步骤。

在允许多候选采样的实验及域外 AndroidWorld 上，显式推理表现出不同收益。这里要把任务分布、采样次数与候选选择方式一起考虑。论文没有支持“每步都写得越长越好”，更不能只根据推理文字是否流畅来判断动作是否可靠。

核心点和不足

UI-TARS 的核心是一套从界面知识到交互经验的训练链：感知数据教模型看什么，grounding 数据教模型在哪里操作，多步轨迹教模型按什么顺序操作，反思样本再教模型怎样处理自己的错误。DPO 则利用同一状态下的正负输出，进一步表达动作偏好。

其中对闭环训练最有启发的，是 失败轨迹要拆开使用。有效前缀、错误位置的替代动作、错误之后的恢复动作，以及偏好负例，承担不同监督角色。把整条失败轨迹全部当作坏数据丢弃，或全部当作示范回灌，都可能浪费或污染监督。

它的局限也很具体：在线任务成功率仍有限；数据筛选和错误纠正需要人工与模型判断；原文没有用完整的逐项消融分离每种数据构造方法的贡献。参数中学到的长期经验也不能自动替代对任意长历史的精确记忆。它展示了一条可操作的数据迭代路线，但距离低成本、完全自主的终身学习仍有差距。

总结

UI-TARS 将截图、任务与历史送入同一个模型，生成 thought 和标准化动作，再根据执行后的新截图继续决策。训练上先建立感知与动作能力，再收集实际交互轨迹，通过纠正、恢复监督和偏好训练利用这些经验。

读完这篇文章，再回看 DAgger，会看到共同的问题意识：训练需要覆盖策略自己访问到的状态。UI-TARS 进一步面对 GUI 数据里的质量判断与失败利用问题，也说明“形成闭环”具体要落实到状态、标签、loss mask 和评测方式上。
