论文阅读：VULCAN

发表于2026-11-19|更新于2026-11-20
|总字数:11.8k|阅读时长:40分钟|浏览量:—

引：VULCAN 由 Stanford、Google 与 NYU 合作完成，第一作者 Zhengfei Kuang 在 Google 实习期间完成这项工作，谢赛宁（Saining Xie）是作者之一。论文要解决的是让多模态大模型在三维场景里 一步一步地 搬动物体。最值得看的是它的分工方式：MLLM 只负责理解指令、规划下一步和判断结果；“物体落到哪个三维坐标、会不会穿模、会不会悬空”交给视觉工具、约束优化器和规则检测；多步任务中前面走错导致后面无路可走的问题，则交给多个 agent 的协作和一个自适应回溯搜索来处理。

背景

人在整理房间时很自然地会拆步骤。比如要把餐桌挪到房间中央，我们会先把桌上的东西拿下来，再把挡路的椅子移开，最后才搬桌子。这里需要两种能力：一是对物理世界的常识，知道桌子一动上面的花瓶就会掉；二是多步规划，知道先做什么、后做什么，每一步之后的场景都还要是合理的。

近来的 MLLM 已经被用于 3D object arrangement，也就是在场景中移动、旋转或插入物体，得到一个合理的布局。但已有工作大多把它当成 单步问题：从初始场景出发，模型分析一次，然后一次性给出到达目标状态的编辑。对“把这本书放到架子上”这样的指令足够了，对“清出一块空地，把大桌子放到中间”这样的指令就不行了，因为后者天然需要好几步，而且步与步之间相互依赖。

把单步扩展成多步，难点在于每一步都必须可靠。单步任务里一次放错只是一个错误结果；多步任务里，错误会传给后面的步骤，并且不断累积。比如第一步把一个瓶子放偏了，第三个瓶子可能就没地方放了。

那么 MLLM 怎样“看懂”三维场景？已有方法大致有两类做法：一类直接给模型看渲染图像等原始视觉表示，另一类给模型看结构化的场景描述，比如场景文件、代码脚本。作者认为这两类做法都不太平衡：前者让 MLLM 去解析它并不擅长的原始 3D 信息，后者给的信息又太简化，不足以支撑精确的空间推理。

作者的切入点是 工具调用。近来 MLLM 的 function calling 和 Model Context Protocol（MCP）让模型可以调用外部程序：模型按约定格式写出“我要调用哪个函数、参数是什么”，外部程序执行后把结果返回给模型。MCP 是一套把这类外部工具接到模型上的通用协议，本文用到的 Blender-MCP 就是一个开源项目，它把 Blender 的场景查询、渲染和执行 Python 代码等能力包装成模型可以调用的工具。这样一来，模型不必自己从像素里估计三维坐标，可以“问”场景：这个像素打到了哪个物体？这块区域里有哪些物体？

基于这个思路，作者分别处理了分析、执行和多步规划三个环节：

  • 分析场景时，给 agent 一套视觉 API，让它主动查询场景布局，而不是被动地读一大堆数据；
  • 执行编辑时，用一个基于约束的无碰撞求解器，把 agent 的高层意图（“放在桌面上、靠近这个像素、面朝相机”）转换成精确的物体位姿；
  • 多步时，把全局规划和单步执行拆给不同的 agent，并设计一个回溯搜索算法，在某一步走不通时退回到较早的状态重试。

具体贡献总结如下：

  1. 一个工具增强的 MLLM，把基于 MCP 的视觉工具和基于约束的求解器结合起来，用于高效的场景分析和物理上合理的摆放。
  2. 一个多 agent 协作框架，把全局规划、单步执行和中间状态检查分给不同角色。
  3. 一个自适应回溯搜索算法，在指数增长的搜索空间里找到一条能到达目标的路径。
  4. 一个新的 3D 多步物体摆放 benchmark，本文方法在上面明显优于已有 baseline。

相关工作

传统的 3D 物体摆放方法通常在大规模三维数据集上训练数据驱动的模型，缺少大语言模型那样的常识推理，难以处理通用指令。近来的一批工作开始用 MLLM 做摆放，由于 MLLM 并没有在大规模三维数据上训练，它们会给模型提供某种中间表示：文本形式的场景描述、代码脚本或渲染图像。其中 FirePlace 和 ScanEdit 已经使用带几何约束的求解器来保证物理合理性，与本文的执行器最接近。但这些工作都局限于单步操作，不能处理需要按顺序摆放、并且要照顾中间状态的多步场景。BlenderGym 等 benchmark 用来评估 MLLM 的 3D 编辑能力，同样不是为复杂的多步摆放设计的。

问题定义

给定一张由固定相机 CCC 从三维场景 SSS 渲染得到的图像 III，以及一条文字指令 TTT，模型要输出一串 单物体摆放 操作，完成用户的目标，同时让所有中间状态都保持物理合理。指令 TTT 可以很抽象（“布置一个用餐区”），也可以是详细的分步说明（“先把书放到架子上，再挪桌子”）。

这里有一点值得注意：模型的“眼睛”是相机 CCC 下的图像，但系统可以通过工具访问底层场景 SSS 中的物体、网格和平面。也就是说，这不是从一张真实照片中恢复三维的问题，场景几何是已知的，难点在于语义理解、规划和精确执行。

每一步操作要满足三个目标：

  • Collision-Free ：每次编辑后，被移动的物体不与场景中其他物体发生碰撞；
  • Floating-Free ：每次编辑后，场景中的所有物体（原本就悬空的除外）都稳稳地放在某个表面上；
  • High Semantic Quality ：摆放结果在语义上合理，并符合用户意图。

与单物体插入或离线的多物体放置不同，这里的问题是 按顺序 的多步移动。每一步，模型都要理解所有子任务与物体之间的关系，制定一个全局一致、可以执行的计划，再可靠地执行它，避免误差积累；必要时，还要在不同的解法分支之间搜索，从先前失误造成的死路中恢复。

多智能体框架

让一个 MLLM 包揽摆放的所有环节，会带来过重的处理负担，也会撞上上下文长度的限制；多步任务需要全局视野，这个问题更加严重。所以作者使用三个分工不同的 MLLM agent。每一步里：

  • Planner 制定这一步的具体摆放计划；
  • Executor 借助工具在三维场景中执行计划；
  • Evaluator 检查执行结果是否合格。

这个分工有两个关键设计。第一， 只有 Planner 拿到全局上下文 ，也就是之前每一步的信息；Executor 和 Evaluator 只在当前这一步的局部范围内工作。第二， 只有 Executor 直接操作三维场景 ，另外两个 agent 只看渲染图像。

我们可以这样理解这个划分：Executor 一次执行要调用好几次工具，返回的物体名、坐标、法向都会堆进它的上下文；Planner 则要看一长串历史渲染图。两者放在同一个模型里，彼此的信息都会成为对方的噪声。拆开以后，每个 agent 只拿到完成自己任务所需的信息。

整个过程就是图 2 中的“Plan–Execute–Evaluate”循环：Planner 给出这一步的计划，Executor 生成编辑候选，Evaluator 和自动的悬空检测决定是否接受；接受后场景进入下一个状态，循环继续，直到 Planner 判断最终布局已经满足用户指令。

全局规划

Planner 的输入是用户指令，以及一段 视觉历史 ：初始场景、每一步编辑后的渲染图，一直到当前场景。它分析这条视觉时间线，弄清场景是怎样一步步变化的，再把过去的状态和用户目标联系起来，决定下一步最合适的动作。

关键在于 Planner 的输出同时包含两样东西：

  • 一条文字指令，比如“把桌子移到黄色和灰色沙发之间”；
  • 一个近似的目标位置，用归一化的二维像素坐标 c=(x,y)\boldsymbol{c}=(x,y)c=(x,y) 表示，x=0x=0x=0 是图像左边，y=0y=0y=0 是图像上边。

作者发现，语言加上空间定位，比只用语言产生的计划歧义更小。

Planner 有两种工作模式，对应两类用户指令：

  • 抽象指令 ：Planner 自己决定怎样拆分任务。它要总结已经做过的编辑，预测剩下的步骤，并检查能否在最大步数（通常为 3 到 6 步）内完成。如果目标已经达成，就输出 <finished>；如果判断在步数限制内不可能完成，就输出 <impossible>，这次尝试直接算作失败。
  • 分步指令 ：用户已经给出了每一步要做什么，Planner 不需要决定做什么，而是在全局上下文中理解当前这一步（同时考虑之前和之后的步骤），把它 改写 成 Executor 只看当前场景就能执行的指令。

为什么需要改写？举一个附录 prompt 中的例子：用户要求“把笔放到苹果原来的位置，并面朝香蕉”。Planner 先安排第一步把苹果移到空处，第二步再放笔。但到了第二步，Executor 只能看到当前场景，“苹果原来的位置”在当前画面里已经没有苹果了，这个说法对它没有意义。Planner 就从历史的第一张图中读出这个位置大约是 (0.52,0.56)(0.52, 0.56)(0.52,0.56)，把指令改写成“把笔放到桌上，面朝香蕉”，再附上坐标 [0.52,0.56][0.52, 0.56][0.52,0.56]。prompt 还要求改写时保留原指令中的度量信息（如 0.5m）、物体名（如 Chair_000）和朝向信息。

所以局部指令和坐标 c\boldsymbol{c}c 合在一起，是 把全局信息压缩后传给局部 agent 的通道 。历史和未来步骤里的空间考虑（比如给后面要放的香蕉留出位置）都要通过这一句话和这一个点交给 Executor。

工具辅助执行

如果让 MLLM 直接执行，它要同时完成理解指令、三维建模和物理合理性检查三件事。Executor 把这些复杂的部分交给外部模块：作者给 MLLM 配了一套基于 MCP 的 API，让它通过交互式的工具调用，把 Planner 的指令和二维坐标 c\boldsymbol{c}c 投射到三维环境中。

执行的大致流程是：

  1. 先做 视觉选择 ，查询场景，定位要移动的物体和承载它的表面；
  2. 再把想要的空间关系翻译成一组 几何约束 ；
  3. 最后调用一个基于优化的求解器，计算出满足约束、无碰撞的位姿。

这三步的细节放在后面的多工具库一节展开。

评估与过滤

Evaluator 拿到 Executor 生成的结果图像和 Planner 给出的局部指令，检查摆放是否合理、是否与指令一致，然后给出五档评分之一：terrible、bad、fair、good、excellent。附录中的评分标准写得很具体：

  • excellent：物理上完全合理，位置也精确符合指令；
  • good：物理上完全合理，但位置只是近似符合（比如在角落附近，而不是正好在角落）；
  • fair：有一处明显缺陷，比如位置对但有轻微悬空或穿模，或者物理合理但放在了正确表面的错误位置；
  • bad：有多处缺陷，或者一处严重缺陷，比如放在了错误的支撑面上（该放桌上却放在了地上）；
  • terrible：物理上不可能（比如悬在半空），或者完全理解错了指令。

MLLM 的判断存在不确定性，Evaluator 偶尔会产生幻觉式的评价，比如给一个完全放错的结果打 excellent。为了缓解这一点，作者使用 基于共识的过滤 ：同时询问多个 Evaluator，把五档评分映射到 −2-2−2（terrible）到 +2+2+2（excellent），取平均，只有平均分为正时才接受这个结果。举个例子，三个 Evaluator 分别给出 good、fair、bad，对应 +1,0,−1+1, 0, -1+1,0,−1，平均为 000，结果不被接受。

除了 MLLM 评估，系统还有一个基于规则的悬空检测。物体摆放完成后，对场景中的每个物体，从其包围盒底面的中心向下发射一条射线，如果在 0.010.010.01 的距离内碰到其他物体，就认为它是接地的。只有初始状态下接地的物体在编辑后仍然全部接地，检测才通过。这一步是确定性的检查，用来补上 MLLM 可能看漏的明显物理错误，违反的结果直接被拒绝。注意它检查的是 场景中所有物体 ，而不只是被移动的那个：如果搬走一张桌子却忘了先拿走桌上的书，书就会悬空，这一步会被拒绝。

视觉标注

为了帮助 agent 推理，作者在输入图像上加了两种标注。

第一种是 坐标网格 ：在图像上画出虚线网格，并在边上标出归一化的像素坐标。图 3(b) 中，直接问 MLLM 三个瓶子的位置，它给出的点落在了瓶子下方的底座上；加上网格之后，给出的点基本落在瓶子上。网格帮助 Planner 给出准确的目标坐标，也帮助 Executor 在调用工具时定位。

第二种是 编辑可视化 ：在图上用一条箭头（附录 prompt 中描述为绿色线段）连接物体的原位置和新位置，原位置的物体画成半透明。图 3(a) 中，只给 MLLM 看编辑前后的两张图，它认为两张图完全相同；加上可视化之后，它能说出“从咖啡桌移到了书架顶上”。这样，Planner 在回看历史时知道每一步做了什么，Evaluator 也能有效地评估最近一次编辑。

自适应回溯

多步执行中，前面某一步的错误可能让后面的步骤无法完成，形成死路。例如，往桌上放东西时前几个摆得不好，后面的物体就没有空间了。这时只重做当前这一步是没有用的，因为问题出在更早的步骤。

为此，作者借鉴经典方法（引用了网络拥塞控制中的加性增、乘性减算法和 KMP 字符串匹配算法），设计了一个自适应回溯搜索。算法维护一个 锚点步（anchor step） ，作为失败后重新开始的位置。锚点按两条规则调整：

  • 某次尝试失败时，锚点退到当前深度的一半；
  • 动作序列达到整个运行中的新的最大长度时，锚点前进。比如这次成功放好了三个瓶子，而之前的尝试最多只放好两个。

这种退法介于“只退一步”和“全部推倒重来”之间。只退一步，如果错误出在更早的地方，就会在死路附近反复打转；每次都从头开始，又会浪费已经做对的步骤。连续失败时锚点不断减半，退得越来越远；一旦有了突破，锚点就跟上新的深度，保住已有的进展。从“成功时慢慢前进、失败时成倍后退”的形式看，它与拥塞控制里的加性增、乘性减确有相似之处。

多工具库

Executor 的任务是把 Planner 基于二维图像的指令，翻译成物理上有效的三维动作。为了跨过这道从 2D 到 3D 的鸿沟，Executor 配备了一个工具库，对应一个清晰的三步工作流程：

  1. 视觉探测 ：查询三维场景，“看到”并识别其中的物体和平面；
  2. 约束构建 ：把摆放计划组织成一组几何约束；
  3. 优化 ：把约束交给求解器，计算出最优的有效位姿。

整个工具库用 Blender 的 Python API（bpy）实现。

视觉探测

作者给 agent 提供了三种视觉探测工具：

  • ListObjectsInArea ：输入图像中的一个矩形区域，返回位于其中或与其部分重叠的物体名。实现上，先渲染场景的实例分割图（instance map），取出该区域内所有像素的实例 ID，再查出对应的物体名。比如输入区域 (0.4,0.6,0.6,0.8)(0.4, 0.6, 0.6, 0.8)(0.4,0.6,0.6,0.8)，返回 [Table, Chair, Plant, Floor]。
  • RayProbe ：从相机出发，沿给定像素坐标发射一条射线，返回第一个命中点的信息：三维位置、命中物体的名字，以及命中平面的名字和法向。比如在 (0.3,0.6)(0.3, 0.6)(0.3,0.6) 处探测，得到物体 Table、法向 (0,0,1)(0,0,1)(0,0,1)、表面 Table-up。这里的“平面”是额外提取出来的：从被射线击中的三角面出发做广度优先遍历，把法向与它的余弦距离在 0.050.050.05 以内的相邻面都收进来，合成一个平面。
  • RenderWithHighlight ：输入一组物体名，渲染一张这些物体分别涂上不同颜色的图，并返回物体与颜色的对应关系。它帮助 MLLM 确认“名字”和“画面里的东西”是怎样对应的。

一次典型的 Executor 运行中，agent 会先调用 ListObjectsInArea 和 RayProbe，拿到相关物体与平面的名字，包括要移动的物体和参照物体。如果只看名字仍有歧义，比如场景中有好几个都叫“Book”的物体，就调用 RenderWithHighlight 来从画面上分辨出正确的那个。prompt 中还特意要求：指令里带颜色信息（如“红色的书”）时不要用高亮渲染，因为高亮会盖住物体本来的颜色。

视觉探测得到的平面有两种命名方式：<物体名>_<面 ID> 是 RayProbe 提取出的平面；<物体名>_up 是物体包围盒的上表面，用于把一个物体叠放在另一个物体上面。这些平面名会在下一步作为约束的参数。

约束构建

找到需要的三维元素后，agent 把摆放计划写成一组约束。支持的约束如下：

  • CloseToPix(obj, x, y) ：物体 obj 在相机 CCC 的视图中应靠近像素坐标 (x,y)(x,y)(x,y)；
  • Contact(obj, dir, p) ：物体 obj 的包围盒朝 dir 方向的那个面应与平面 p 接触；
  • NoOverhang(obj, dir, p) ：物体包围盒朝 dir 方向的面应完全落在平面 p 的凸包之内；
  • Distance(obj, obj₂, dist) ：obj 与 obj₂ 之间的欧氏距离应接近 dist；
  • FaceTo(obj, obj₂/p) ：物体 obj 的朝向应指向 obj₂ 的中心，或与平面 p 的法向一致；
  • Rotate(obj, degree) ：物体逆时针旋转 degree 度。

优化

目标像素 ccc 和前面得到的约束已经把解限定在一个很小的范围内，所以作者采用一种高效的基于采样的方法，见 Algorithm 1：

具体来说，整个过程分四步：

  1. 扰动目标像素 。以 ccc 为中心、标准差 0.20.20.2 的高斯分布，采样出一批变体坐标 c′c'c′，分别替换 CloseToPix 中的目标。作者称这一步受数值分析中预条件（preconditioning）技术的启发。
  2. 并行优化 。对每个变体坐标优化一个位姿。位置初始化为从该像素发出的射线与场景的第一个交点（由 RayProbe 得到），旋转初始化为零，除非有 Rotate 约束。使用 AdamW 优化 800 步，学习率从 10−110^{-1}10−1 线性衰减到 10−410^{-4}10−4。
  3. 按误差预筛 。用原始的、没有扰动的 ccc 重新计算每个解的约束 loss，丢掉超过阈值 τ=10−1\tau=10^{-1}τ=10−1 的解。
  4. 碰撞检测 。按误差从小到大检查剩下的解，返回第一个不发生碰撞的位姿；全部碰撞则返回失败。

为什么要扰动坐标？Planner 给出的 ccc 本来就是一个近似位置，如果它恰好落在另一个物体上，从这里出发的优化很可能卡在一个会碰撞的解上。在 ccc 周围撒一批起点，就得到了一批分布在目标附近的候选位置，再由碰撞检测挑出可行的那个。第 3 步再用原始的 ccc 把关，避免候选偏得太远。从数值上看，如果只有 CloseToPix 一项有误差，0.5 d2<0.10.5\,d^2 < 0.10.5d2<0.1 对应的像素偏差 ddd 可以接近 0.450.450.45，几乎是半张图；而 Contact 和 NoOverhang 的权重分别是 100 和 20，所以这个阈值更多是在筛掉“没贴住表面”“伸出了边缘”的解，对位置偏差相对宽松，位置是否合适主要还得靠后面的 Evaluator。

碰撞检测也值得一提。标准的 bpy 并不开放 Blender 原生物理引擎的碰撞检测，作者用三个 geometry modifier 来近似：先用 Solidify 把网格加厚，保证墙、地板这类薄结构也能被可靠检测；再用 Remesh 把源物体和目标物体转成流形网格；最后用 Boolean 计算两个物体相交部分的体积。如果相交的几何深入物体包围盒超过 0.010.010.01，就判定为碰撞。

实验

所有实验都使用 Gemini-2.5-pro 作为 MLLM。摆放框架，包括约束求解器和视觉 API，用 Blender 的 Python 扩展包实现，并与 Blender-MCP 库集成。每一步摆放使用 3 个 Evaluator，并行执行 4 次尝试，从合格的结果中选平均评分最高的那个。如果所有尝试都没有找到合格的解，这一步就记为失败，系统进入回溯。实现上还有一个提前终止：如果所有 Evaluator 都给当前编辑打了 good 或 excellent，就直接接受它，跳过剩下的尝试。

数据集与指标

评测数据集包含 25 个精选场景，来自 BlenderKit、InfiniGen 和 BlenderGym，共 111 个单元任务。为了公平比较，所有 baseline 都接收相同的分步指令，执行相同的操作序列。任务被有意设计成步骤之间相互依赖：如果前面的步骤执行不当，后面的步骤就会受影响。

每一步都计算以下指标，再对所有任务取平均：

  • Collision Rate ：被移动的物体与其他元素发生碰撞的步骤所占比例，越低越好；
  • Floating Rate ：导致场景中任何物体失去支撑（悬空）的步骤所占比例，越低越好；
  • Plausibility ：摆放的物理真实性，由 MLLM 打分，0（差）到 4（好），越高越好；
  • Consistency ：结果与用户指令的一致性，由 MLLM 打分，0 到 4，越高越好。

后两项的评审 prompt 改编自 FirePlace，评审 agent 同时看所有步骤的结果，在全局上下文中给每一步打分，每个样本使用 5 个评审取平均。论文没有明确说明评审使用的是哪个 MLLM。

  • 工具库影响最大 。去掉求解器和视觉工具后，碰撞率和悬空率回到 0.5 和 0.7 左右，评分也明显下降。不过它仍然比原始的 Blender-MCP baseline 好（Consistency 3.103 对 2.973），作者把这部分提升归于多 agent 设计和回溯。完全不用 MCP、直接写脚本的变体最差，说明让 MLLM 通过函数级调用操作场景，比让它直接写底层代码更可靠。
  • 回溯处理的是少数难例 。去掉回溯后，模型偶尔会接受次优的解，碰撞率和悬空率变成很小但非零的 0.036 和 0.054。作者认为是流水线其余部分的鲁棒性让这类情况在 benchmark 中比较少见。
  • 单 agent 的问题出在推理质量 。单 agent 变体仍然有求解器和检测，所以碰撞率和悬空率还是 0，但 Plausibility 和 Consistency 分别降到 3.623 和 3.328，是除工具类消融外下降最多的。这支持了拆分全局规划与局部执行的设计。
  • Planner 坐标的作用较小 。去掉坐标后，两个评分只下降了 0.024 和 0.066，是所有变体中影响最小的。也就是说，在这个 benchmark 上，把全局信息传给 Executor 的工作主要由改写后的局部指令完成，坐标更多是在指令之上做消歧和微调。

可视化结果

图 7 展示了 Planner 的弹性规划。简单任务“把书放到架子上”只用一步就结束；复杂任务“在椅子所在的位置布置一个用餐区”需要多步，而且两次运行给出了不同的计划：一次先把椅子移开，把桌上的书拿到床上，再挪桌子、摆椅子；另一次先把书放到书架顶上，然后直接把桌子移到椅子前面，再调整椅子。两条路径都到达了合理的终点。

在这个设定下 VULCAN 的 Plausibility 达到满分 4。Consistency 上的差距更大，这正是单步方法应付不了的地方：比如“把长桌移到架子前面，那里现在放着椅子和植物”，单步方法只能直接搬桌子，结果与椅子、植物冲突；VULCAN 会先把椅子和植物移走，再搬桌子。

价值与不足

这篇文章的核心是 接口设计 ：它仔细划分了 MLLM 和传统几何计算各自应该承担什么。MLLM 擅长理解“用餐区”“对称”“给后面的物体留位置”这类语义，不擅长给出精确的三维坐标；优化器擅长让物体严丝合缝地贴在表面上，却不懂指令。VULCAN 在两者之间放了两层接口：

  • Planner 和 Executor 之间是“一句局部指令 + 一个二维像素坐标”，把全局上下文压缩成单步可执行的信息；
  • Executor 和求解器之间是一套离散的约束词汇，把“放在哪里”从连续位姿的回归问题，变成从有限关系中做选择、再由优化求数值的问题。

在这两层接口之外，Evaluator 投票和规则检测负责“守门”，回溯搜索负责从死路中恢复。实验也基本对应了这个分工：去掉工具库影响最大，去掉多 agent 主要损失语义质量，去掉回溯则让少数有伪影的结果漏过。

不足之处可以从以下几个方面看：

  • 依赖完整、已知的三维场景 。视觉探测需要实例分割图、射线求交和物体网格，求解器和碰撞检测也都在 Blender 场景中运行。系统的输入虽然是一张图像，但前提是图像背后有一个可以随时查询的三维场景。要用于真实照片或真实机器人，需要先有重建和实例分解，作者没有讨论这部分。
  • 只有单一视角 。为了控制上下文长度、保持推理质量，系统只支持一个相机视角。作者指出，这会影响需要新视角观察的任务，比如把椅子放到墙后面看不见的空间。
  • 规划错误会拖慢效率 。附录图 9 上半部分中，Planner 的第一步就去搬桌子，没有先拿走桌上的书，导致书悬空。悬空检测能拒绝这个结果，回溯也能让系统换一条路，但这种试错显著降低了效率。
  • Evaluator 会集体出错 。图 9 下半部分中，椅子的位置明显不对，三个 Evaluator 却都给了 excellent。投票能过滤掉单个 Evaluator 的偶然幻觉，但三个 Evaluator 用的是同一个模型、看的是同一张图，它们的错误很可能是相关的，平均起来并不能抵消。
  • 约束词汇本身有边界 。只优化 yaw，物体不能倾斜或倒放；平面基于包围盒或局部共面面片，形状不规则的支撑面可能表达不准；每一步只移动一个物体，带着上面东西的托盘必须先拆开再搬；悬空检测只看包围盒底面中心下方是否有支撑，不做受力和稳定性分析。
  • 成本没有报告 。每一步有 4 次并行尝试、每次 3 个 Evaluator，再加上 Executor 的多轮工具调用和可能的回溯，一个任务的 MLLM 调用次数相当可观，论文没有给出耗时或调用量。
  • 评测规模较小 。benchmark 由作者构建，共 25 个场景、111 个单元任务（抽象指令设定只有 12 个场景），质量评分主要依赖 MLLM 评审，人类评估也只报告了相对胜率。

总结

VULCAN 的工作过程可以归纳成一个循环：

  1. Planner 看着用户指令和历史渲染图，决定这一步移动哪个物体，给出一句只依赖当前场景的局部指令和一个目标像素坐标；
  2. Executor 用视觉工具找到相关的物体和平面，写出一组几何约束，交给求解器算出无碰撞的位姿；
  3. 多个 Evaluator 投票，加上规则式的悬空检测，决定是否接受这一步；某一步走不通时，回溯算法退回到较早的锚点重新尝试。

它说明的一个思路是：让大模型在三维场景中做精确操作时，不一定要让模型直接输出数值，可以把它的输出改成 对工具和约束的选择 ，并用确定性的检查兜底。这和 Lucida 中 GizmoAct 的思路有相通之处，两者都让 VLM 通过可执行的接口和视觉反馈与场景交互，只是 VULCAN 的反馈来自约束优化和评估投票，GizmoAct 则是多轮的编辑操作。

如果要继续读，可以先看 FirePlace，它是本文 Executor 中“MLLM + 几何约束求解”部分的直接前身；再看 LayoutVLM，它同样把 VLM 的输出接到可微的布局优化上，但针对的是整体场景布局；BlenderAlchemy 则代表了另一条路线，让 MLLM 通过写脚本和视觉评估迭代编辑场景。
