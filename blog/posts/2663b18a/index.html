论文阅读：LiteReality-Agent

发表于2026-11-24|更新于2026-11-24
|总字数:10.2k|阅读时长:35分钟|浏览量:—

引：LiteReality-Agent 由剑桥大学、帝国理工学院等机构的研究者完成（Zhening Huang、Yueyan Li、Johnathan Chiu、Shangzhe Wu 等），是 LiteReality (Huang et al., 2025) 团队在实景转仿真（Real-to-Sim）方向上的延续，物体程序化建模部分也直接承接了 Articraft (Zhou et al., 2026)。这篇工作最值得关注的设计，是把「从消费级 RGB-D 扫描重建可交互三维场景」改写成一道编程任务：整个房间就是一个可执行的 Room.py 脚本，由代码智能体在「观测—编辑—验证」（observe–edit–verify）闭环里持续取证、改代码、重新编译并过物理质检。更有意思的是作者和前沿通用代码智能体（GPT-6 Astra、Fable 5.1）的对照实验——仅仅把点云和深度图喂给通用模型，像素与深度误差确实会大幅下降，但家具穿模反而变多；真正决定重建能否直接进仿真器的，是面向三维场景设计的取证工具与几何/支撑门控。

图来自原论文 Figure 1：LiteReality-Agent 将消费级 RGB-D 扫描转化为可执行的 Room.py 程序，编译后得到逼真、可交互且可直接导入仿真环境的 3D 室内数字孪生。

背景

想从真实房间的扫描数据里建出一个能直接跑机器人仿真、物理交互的数字孪生，光把点云拼起来或者重建出一整块大网格是不够的。点云法（如 ORB-SLAM3、VGGT）和常规网格重建（如 Atlas、NeuralRecon）得到的是「一整坨」静态几何，既分不清哪个抽屉能拉、哪扇门能开，也没有质量、摩擦和碰撞体信息。要让场景真正「可交互、可仿真」，系统必须同时搞定四件事：理解房间壳体结构、重建独立物体及其铰接关节、估计材质与物理参数、以及理顺物体间的支撑与碰撞关系。

沿着这个目标，现有路线各有各的卡点：

  • CAD 检索与确定性管线：Scan2CAD (Avetisyan et al., 2019)、DiffCAD (Gao et al., 2024) 靠检索对齐现成 CAD 资产，前作 LiteReality (Huang et al., 2025) 也把场景解析、资产检索、外观恢复和装配串成了多阶段流水线。这类确定性管线在预设模板内很稳，但一旦遇到资产库里没有的异形家具、墙面杂物或特殊布局，系统缺乏临场排查和修正的能力。
  • 组合式生成与可微渲染：像 CAST (Yao et al., 2025) 用 3D 生成模型逐个造物体再摆进场景，PSDR-Room (Yan et al., 2023) 用可微渲染反推几何与材质，但要把大规模真实扫描稳定地做成无穿模、带关节的仿真环境，整体鲁棒性依然不够。
  • LLM 驱动的 3D 场景生成：Holodeck (Yang et al., 2024)、SceneCraft (Hu et al., 2024)、SceneSmith (Pfaff et al., 2026) 等工作已经证明大语言模型能写代码、排布仿真场景；在物体层面，Articraft (Zhou et al., 2026) 把铰接资产生成做成了带专用 SDK 和自动验证的编程任务。不过这些系统大多是「凭空生成」，缺少与真实扫描观测对齐的机制。
  • 通用代码智能体：像 GPT-6 Astra 和 Claude Fable 5.1 这样的新一代代码智能体已经具备很强的 3D 理解与建模能力，但如果直接让它们读照片和点云去写 Blender 脚本，它们没有同机位对比、墙面度量网格和物理质检护栏，很容易顾此失彼——画面看着像了，家具却飘在空中或者互相穿模。

换句话说，现在缺的不再是单个生成模型，而是一套能把通用代码智能体编排起来、把修改锚定在真实扫描证据上，并强制守住几何与物理底线的系统框架。为此，作者提出了 LiteReality-Agent，核心贡献可以概括为三点：

  1. 将真实室内 RGB-D 重建表述为以 Room.py 为持久化工作区的编程任务，所有场景结构、物体实例、材质和后续编辑都通过可执行代码统一管理，天然支持复现与自然语言二次编辑。
  2. 设计了「场景初始化 + 智能体精修」两阶段框架：第一阶段通过 Layout Agent 与双路由物体重建产出干净的初始场景；第二阶段构建 observe–edit–verify 闭环，配套多尺度视角选择、同机位渲染对比、墙面拼接度量网格、PBR 材质检索以及独立的碰撞与支撑质量门控。
  3. 实现了面向 MuJoCo (Todorov et al., 2012) 的物理仿真导出，并在 10 个真实室内场景上系统对比了 LiteReality 及 GPT-6 Astra、Fable 5.1 两个前沿代码智能体，在视觉保真度、几何一致性与人工感知评测上均取得最高均分。

方法

LiteReality-Agent 的输入来自消费级移动设备的 RGB-D 扫描及检测结果，输出是一个可直接编译成三维场景的可执行 Python 程序 Room.py（以及各程序化资产对应的 object.py），并进一步导出为带物理属性与关节的 MuJoCo 仿真场景。整个系统分成两个阶段：第一阶段 场景初始化 先修好布局并造出主要物体，搭出初始版 Room.py；第二阶段 智能体精修 在有界预算内反复取证、改代码、重渲染并过几何与支撑质检。先看整体数据流与闭环结构：

flowchart TD
    IN["输入：RGB-D 帧 + 相机标定 + 点云 + RoomPlan 布局与物体检测框"] --> LA["Layout Agent：构建场景图、确定性修复 + 可选图像推理修复"]
    LA --> ROUTE{"物体双路由重建"}
    ROUTE -->|结构规整 / 含关节| PROC["程序化生成（Articraft 路线，输出 object.py + 关节与物理元数据）"]
    ROUTE -->|外观复杂 / 静态| GEN["Image-to-3D 生成（TRELLIS.2 + 网格质检与椅子重试循环）"]
    PROC --> ASM["场景装配：生成初始 Room.py（壳体 + 物体实例 + 材质）"]
    GEN --> ASM
    ASM --> LOOP["进入智能体精修循环（预算上限 T，最后 10% 禁用探索强制收尾）"]
    LOOP --> TOOLS["取证工具集：select_views / render_and_compare / stitch_wall / measurement / fetch_material"]
    TOOLS --> EDIT["代码智能体分析差异并编辑 Room.py / object.py（四阶段有序精修）"]
    EDIT --> REBUILD["重新编译场景并过 QC 门控（网格碰撞检测与局部修正 + 支撑接触检查）"]
    REBUILD -->|存在未解违规且预算未尽| LOOP
    REBUILD -->|通过门控或预算结束| EXPORT["MuJoCo 仿真导出（质量、惯量、凸分解碰撞体、自由/铰链/滑动关节）"]

可以看到，第一阶段负责把充满噪声的原始扫描变成「结构干净、尺度正确、没有明显硬伤」的初始程序，第二阶段则把精细材质、墙面设施、小物件和局部几何细节交给代码智能体逐步补齐。下面结合原论文的整体管线图，按输入、场景初始化、智能体精修和仿真导出四个部分拆开讲清每个模块的具体做法。

输入

系统的输入由配套的 LiteReality Scan 采集应用提供，包含五类紧密关联的数据：

  • RGB 图像帧：提供物体外观、墙面材质、灯具和装饰细节的视觉证据。
  • LiDAR 深度图与置信度图：提供几何度量证据，并在后续墙面拼接和视角筛选时用于判断可见性。
  • 相机标定信息：包含每帧的内参、外参位姿和时间戳，用来把三维点反投影回照片，或把重建好的场景渲染到与真实照片完全一致的机位上。
  • 派生点云：由 RGB-D 观测融合成的稀疏/稠密三维表面，直观反映已观测区域和缺失盲区。
  • RoomPlan 检测结果：给出房间墙体、门窗开口的初始壳体结构，以及带语义类别、度量尺寸和位姿的初始物体 3D 包围盒。

这里要注意一点：RoomPlan 检测框只是初始布局估计，往往存在墙体穿插、物体悬空、尺寸偏大或把相邻物体错误合并等问题，不能直接拿来当最终布局，否则后面生成的物体也会跟着错位或缩放失真。

场景初始化

阶段一沿用了 LiteReality (Huang et al., 2025) 先拆解房间壳体与独立物体、最后再装配的思路，但做了一个关键替换：不再从固定资产库检索模型，而是直接基于当前扫描自身的图像证据生成每个物体。在真正生成物体之前，先由 Layout Agent 把布局理顺。

布局智能体

Layout Agent 首先把房间和物体组织成一张场景图（scene graph），节点包括房间壳体、结构表面、门窗开口和物体，边则记录支撑、贴墙、开口宿主、功能分组和潜在冲突。这张图刻意区分了两对容易混淆的关系：

  • 物理支撑 与 功能分组：每个物体只能有一个支撑父节点（地板、墙面、天花板或另一物体），否则会被标成悬空；但一把椅子在功能上属于旁边的书桌，物理上却是由地板支撑的。拆开这两层关系后，系统既能让书桌和椅子保持相对位置一起平移，又不会错误地认为「桌子托着椅子」。
  • 非法穿模 与 合理包围盒重叠：两张书桌的包围盒撞在一起显然是检测出错，但一把椅子推进餐桌底下时，两者的外接长方体天然会重叠。场景图通过类别感知的例外规则，避免把合理嵌套误判成冲突。

有了场景图后，Layout Agent 会先跑一轮确定性几何修复搜索，尝试把跑出房间、插进墙里、悬空或冲突的包围盒做贴墙、靠角、分离和微调尺寸；如果纯几何搜索解决不了（比如检测器把两个柜子误合并成一个大框，或者尺寸错得离谱），再唤醒可选的图像引导智能体，把当前框、周围物体、违规信息和参考照片交给它，让它提议平移、缩放、贴一面/两面墙，或是把合并框拆回原始成员。

为了防止智能体「为了消冲突把房间改得面目全非」，所有候选修改都受严格的累计保真度上限约束，且相对于原始扫描累计计算：

  • 水平位移累计不超过 0.6 m0.6\,\text{m}0.6m，垂直位移累计不超过 0.08 m0.08\,\text{m}0.08m；
  • 桌子、书桌、椅子、沙发、床等主要家具单轴尺寸变化不超过 15%15\%15%，其他类别不超过 35%35\%35%；
  • 允许拆分错误合并的框，但禁止通过删除已测物体来消除违规。

候选方案只有在不破坏已有锚定、满足累计上限且先降违规总数、再降总误差幅度的前提下才会被接受，最多跑 6 轮智能体辅助修复。举两个附录里的真实例子：在办公室场景中，Table1 和 Chair1 共同平移了 (0.1445,0.0124,0) m(0.1445, 0.0124, 0)\,\text{m}(0.1445,0.0124,0)m，14.5 cm 的协同位移在不改变尺寸的前提下保留了桌椅相对位置并消除了 2 处违规；在厨房场景中，Storage3 和 Dishwasher0 各移动约 5.3 cm5.3\,\text{cm}5.3cm、两个水平维度各缩小约 8.5 cm8.5\,\text{cm}8.5cm，解决了 3 处墙体/边界穿插。在全部 10 个评测场景的 107 个初始框里，这一步把布局检查器的违规数从 30 降到了 0（29 个框移动、4 个框缩放，且全部由确定性搜索即已解出）。

物体重建与物理元数据

拿到修正后的包围盒，系统先为每个物体挑选扫描视角，用图像生成模型生成一张去除了背景杂物的干净参考图，再按物体特性分两条路由重建：

  1. 程序化生成路由（结构规整或需要铰接交互的物体，如橱柜、洗碗机、桌架）：沿用 Articraft (Zhou et al., 2026) 的思路，让代码智能体编写独立的 object.py 脚本，显式定义几何体、独立活动部件、关节轴、枢轴点和运动限位。
  2. 图像到 3D 生成路由（外观复杂且基本静态的物体，如沙发、软包椅）：调用 TRELLIS.2 (Xiang et al., 2026) 直接从干净参考图生成带纹理的三维网格。

生成式 3D 模型偶尔会产出畸形几何，因此网格要过一遍自动筛选，专门拦截异常长宽比、悬空碎块、大片平坦边界以及底部粘连地板/背景的资产。针对容易出问题的椅子类物体，系统还设了有限次重试循环——质检失败就换随机种子重新生成参考图和网格；如果预算耗尽仍未通过，则保留原资产并把未解问题记入日志。

更关键的是，物理属性在这一步就与视觉资产同步编译，而不是等最后导出仿真器再临时拼凑：

  • 质量与惯量：若程序化脚本已手写质量或密度则直接保留；否则按「类别占有密度 × 包围盒体积」估算总质量，再按各连杆几何体积分配，并从连杆几何计算质心与惯性张量（退化网格退回凸包或包围盒近似）。
  • 摩擦与碰撞体：未指定时由材质名称先验给出摩擦系数和恢复系数；近凸部件直接用单凸包，大型凹部件做凸分解，且分解预算随连杆质量调节，避免轻小物体引入过多接触面拖慢仿真。
  • 单物体 MuJoCo 预检：每个资产在装配进房间前先独自进 MuJoCo 跑三项测试——短距离跌落、逐个关节释放、倾斜重力滑动，提前抓出穿模、部件脱落、数值发散或异常滑动，并区分关节撞到自身框架与需要特定开启顺序的相邻门板碰撞。

场景程序 Room.py

房间壳体和所有物体资产准备好后，按修正后的尺度和位姿装配成一个完整的 Room.py 脚本。Room.py 负责房间壳体、物体实例化、材质配置以及后续新增的几何体，程序化资产则保留各自的 object.py。这份代码就是整个系统的持久化工作区：之后任何修改都以代码编辑的形式落盘，重新执行脚本就能完全复现当前三维场景。

智能体精修

阶段一搭出的初始房间虽然布局规整、大件齐全，但墙面贴图往往还很粗糙，白板、插座、吊灯、桌面小物件也还没补齐，部分程序化资产的细节和真实照片仍有差距。阶段二的智能体精修把 Room.py 交给代码智能体，在一个有界的 observe–edit–verify 循环里持续打磨。

原论文 Algorithm 1 概括了这个循环的执行逻辑：

  • 初始状态：env 指向当前 Room.py，tools 为系统工具集，observations 为原始扫描数据，history 置空，turn = 0，qc_passed = false。
  • 循环条件：当 turn < T 且 not qc_passed 时，每轮由 LLM 根据 (observations, env, tools, history) 产出一步或多步工具调用 actions，执行后将 (actions, result) 写入 history。
  • 门控触发：只要某步 result 实质修改了场景代码，系统就调用 QC(env, observations) 重新编译并做几何/支撑检查，把 qc_passed 标志和具体违规反馈 feedback 追加回 history，供下一轮继续修复。

取证工具

通用代码智能体自己写 3D 场景时最容易「盲人摸象」——要么翻几百张扫描图看花眼，要么凭感觉猜一个坐标写进代码。LiteReality-Agent 把三维取证拆成了五个专用工具（配合通用的 bash、glob、read、edit 文件操作）：

工具名 核心用途
select_views 按房间、单面墙或单个物体三个层级挑选信息量最高的扫描帧
render_and_compare 用相同标定相机渲染当前场景，与真实照片并排标注对比
stitch_wall 将多帧投影到度量墙面，拼出正视墙面参考图与覆盖率掩码
measurement 在拼接墙面或场景中以米为单位读取真实位置与尺寸
fetch_material 检索 PBR 材质贴图（颜色、粗糙度、法线）并按观测调整色调

这里面有几个很实用的工程巧思：

  • 三层视角选择与同机位对比：select_views 和 render_and_compare 都支持 房间级 → 墙面级 → 物体级 的逐层下钻。房间级贪心挑选能互补覆盖多面墙的帧，对比图里直接标出可见物体的名称；墙面级按墙体在画面里的投影面积排序，对比图只勾出选中墙面的轮廓；物体级依据渲染清单的可见度找最清晰的帧，对比图框出目标包围盒；同时用最小帧间隔滤掉几乎重复的相邻帧。因为渲染图和照片严格共用同一组标定相机参数，智能体不需要自己脑补视角对齐，一眼就能把房间级的偏差追溯到某面墙或某个物体。并且每次对比前都会先重新编译修改过的 Room.py 和 object.py，确保看到的永远是最新状态。
  • 墙面拼接与度量网格：墙上的白板、挂画、窗户到底离地多高、宽几米？靠人眼从透视照片里估很容易偏十几厘米。stitch_wall 在检测出的墙面上铺一层度量网格，把每个像素对应的三维点反投影到候选标定帧里，优先挑正面、居中、近距离且深度可见的像素直接填充（不做模糊混合），同时输出一张覆盖率掩码标出未拍到的盲区。接着 measurement 往正视墙面上叠一层米制刻度网格——红刻度标沿墙水平距离，蓝刻度标离地高度。

图来自原论文 Figure A8(d)：厨房场景中一面带白板的拼接正视墙面叠加度量网格，红色刻度为沿墙水平距离（米），蓝色刻度为离地高度（米），智能体可直接读出白板四边坐标写入 Room.py。

看上面的白板例子，智能体不用猜，直接顺着红蓝刻度就能读出白板左右边界和上下高度，原样写进 Room.py。作者也专门提醒：平面投影会把凸出墙面的物体拉变形，所以遇到灯具、家具和桌面杂物时，智能体仍要回看原始采集帧。

  • 四阶段有序精修流：为了让智能体不乱改，编排框架按固定顺序引导四个精修模块：第一步匹配墙面与地面材质（通过 fetch_material 拉取 PBR 贴图并调色，保留纹理空间图案的同时对齐真实色调）；第二步补齐固定设施与灯具；第三步放置桌面和地面上的小物件；第四步对已有的程序化资产做多视角渲染检查，继续精修其几何、外观与关节。每一步都把所有新增几何打包成具名物体，并强制写明 rests_on（支撑关系）或 attached_to（附着关系），让后续编辑也能顺着语义和依赖关系安全改动。

预算控制与质量门控

精修什么时候该停？视觉相似度很难定一个放之四海而皆准的自动阈值——设太高会死循环烧预算，设太低又草草收场。LiteReality-Agent 的做法是把停止条件和质量判定分开：

  • 预算控制：每个精修会话设定最大轮数和工具调用上限。在最后 10%10\%10% 的调用预算里，系统通过前置钩子禁用探索和自检类工具（若底层适配器不支持钩子则硬停），逼着智能体收尾并保存代码。但耗尽预算终止绝不等于质检通过，保存后的程序依然要过重建与验证。
  • 独立的网格碰撞门控：阶段一的布局修复只看粗包围盒，到了阶段二物体有了精细网格、还添了新物件，必须拿真实三角网格查穿模——特别是椅子和桌子这种包围盒允许重叠、但椅腿和桌板绝不能真插在一起的组合。系统先用网格相交判定碰撞，再用凸近似估计水平修正平移，在有界预算内移动未锚定物体、把累计位移写回 Room.py 并重建复查；局部平移解不了的冲突直接打回给精修循环。
  • 独立的支撑接触门控：不穿模不代表没问题，物体完全可能悬空飘着。验证器把每个物体底面与它声明的支撑面顶部逐一核对，并检查底面投影重叠率：
    • 悬空缝隙 >1 cm> 1\,\text{cm}>1cm 或穿透深度 >2 cm> 2\,\text{cm}>2cm 直接阻塞；
    • 缺少或未知的支撑声明直接阻塞；
    • 底面投影落在支撑面上的比例不足 50%50\%50% 报出复查；
    • 已识别但未显式声明支撑的落地家具按 5 cm5\,\text{cm}5cm 容差兜底检查，附着在墙面或天花板上的固定件则豁免重力支撑检查；
    • 同时确认铰接资产仍保留独立的活动部件。

除了这些确定性几何门控，系统还支持接入基于检查清单的视觉审查来补充外观反馈。

仿真导出

当 Room.py 通过精修与门控后，导出器汇总四份数据生成可直接运行的 MuJoCo 场景（MJCF）：

  1. Room.py 中的房间壳体几何（墙体会绕开门窗开口拆成结构化长方体）；
  2. room_layout.json 中的物体位姿与支撑声明；
  3. Room.glb 中的外观网格与材质；
  4. 每个物体在阶段一编译好的物理元数据记录。

导出时，墙面与附着固定件锁定不动，可移动家具分配自由关节（free joint），程序化铰接部件保留对应的铰链（hinge）或滑动（slide）关节，并为带力矩元数据的关节配置电机执行器。独立的凸分解碰撞体保留了桌底和柜内的可用空间，不会被一个实心大盒子堵死；如果精修阶段改过物体尺寸，导出器会自动按体积缩放派生质量并重算惯量（手写质量则原样保留）；新增且缺少物理记录的小物件会在导出时补算兜底质量和碰撞体，并在导出报告中如实记录。

实验

实验设置

作者在 10 个真实室内场景（共 620 个采集视角，每个场景 27–91 帧）上评测 LiteReality-Agent，对比三类基线：

  • LiteReality (Huang et al., 2025)：确定性多阶段检索与重建管线；
  • GPT-6 Astra（运行于 Codex）：通用前沿代码智能体，分别测试纯照片输入（RGB-only）和附加扫描输入（+Scan）；
  • Fable 5.1（运行于 Claude Code）：另一款通用前沿代码智能体，同样测试 RGB-only 和 +Scan。

其中 +Scan 条件向基线提供与 LiteReality-Agent 完全相同的扫描信息，包括对齐的 LiDAR 深度与置信度图、相机标定、点云和 RoomPlan USDZ 布局。所有重建结果都对齐到采集相机坐标系（不改动场景尺度和单个物体位姿），在 Blender 5.2 Cycles（64 spp + OptiX 降噪）中按采集位姿渲染到 960×720960 \times 720960×720。为了公平比较几何与材质，同一场景下所有方法共享对应 LiteReality-Agent 场景的灯光、世界照明和色彩管理设置，但各自保留自己的材质、纹理和自发光（注意：共享灯光并未针对参考照片单独校准，且评测在采集视角上进行，而非未见新视角）。

这个反差直接点出了 LiteReality-Agent 的核心价值：给前沿模型塞入原始 RGB-D 扫描，足以帮它们把宏观尺度和深度拉齐，但如果没有面向三维重建设计的布局修复、校准取证工具以及网格级碰撞/支撑门控，通用智能体很难同时兼顾几何贴合与物理无穿模。当然，作者也如实说明，这组对照验证的是完整系统的整体效果，并未把编排框架与 Layout Agent、双路由物体重建拆开做单因素消融。

核心价值与不足

值得关注的设计

这篇论文最有启发性的地方，在于把三维实景重建重新定义为一个以可执行程序为持久状态、以校准取证与确定性门控为护栏的智能体系统工程。以往实景转仿真要么靠固定流水线硬写规则（泛化差），要么指望端到端大模型一步出结果（几何与物理约束极难守住）。LiteReality-Agent 把分工划得很清楚：让大语言模型负责语义理解、程序编写和开放式细化，而把相机标定投影、米制墙面测量、三角网格求交、支撑容差校验这些容易算错的硬活全部做成确定性工具与门控。更难得的是，这种 harness 架构不绑死在某一代底座模型上——随着未来代码智能体的视觉和编程能力继续变强，这套工具与门控框架可以直接吃到底座升级的红利。

局限与未解问题

结合原论文附录 F 的自述以及实验边界，目前还有三处明显的局限：

  1. 物理参数缺乏真实测量真值：物体的质量、惯量、摩擦系数和恢复系数主要靠语言模型推理、类别占有密度先验和几何体积估算，缺少真实世界的物理测量真值。因此「能导进 MuJoCo 且不穿模、不悬空」只能说明场景在几何和结构上可仿真，并不能保证其动力学响应与真实物体一致。
  2. 布局自洽不等于真实布局精确：RoomPlan 的初始检测框本身就可能存在尺寸和位姿误差；Layout Agent 的保真度约束和后续的碰撞/支撑门控虽然保证了输出场景内部自洽，甚至在采集视角上看起来很贴合，但这并不保证恢复出的布局与真实物理尺寸完全吻合。未来需要把图像观测更紧密地耦合进布局优化，并引入真值测量基准来评估。
  3. 评测规模与消融颗粒度有限：当前基准只覆盖 10 个室内房间，视觉指标仅在采集视角（而非新视角）下计算，且所有基线共用了 LiteReality-Agent 的场景灯光；此外，实验没有对 Layout Agent、双路由物体重建、墙面度量工具和质量门控做逐项消融，还难以定量拆解每个组件各自的边际贡献。

总结

回顾整条链路，LiteReality-Agent 用三个紧密衔接的环节打通了从消费级 RGB-D 扫描到可交互仿真场景的闭环：

  1. 先修布局、双路由建资产：用场景图区分物理支撑与功能分组，在累计保真度上限内修净 RoomPlan 噪声，再将物体分流至程序化 object.py（带关节与物理元数据）或 TRELLIS.2 网格，装配成初始 Room.py。
  2. 在可执行的 Room.py 上闭环精修：借助三层视角选择、同机位渲染对比、正视墙面拼接度量网格和 PBR 材质检索，按材质→设施→小物件→资产精修四步迭代修改代码，并由有界预算与独立的网格碰撞/支撑门控兜底。
  3. 带物理属性导出仿真：汇总壳体、位姿、外观与物理元数据导出至 MuJoCo，同时保留一份人类和智能体都能直接读写的场景代码。

如果对这条「代码即三维场景 + 智能体闭环逆向图形学」的路线感兴趣，建议顺着两条线索继续读：一是本文的直接前作 LiteReality (Huang et al., 2025) 与物体级程序化铰接资产系统 Articraft (Zhou et al., 2026)，看清楚系统如何从确定性管线和单物体 SDK 演进到全场景智能体编排；二是同期在程序化生成与实景转仿真方向上的代表工作 SceneSmith (Pfaff et al., 2026) 与 Agentic Real2Sim (Chen et al., 2026)，对比不同系统如何设计智能体的观测工具与物理验证闭环。
